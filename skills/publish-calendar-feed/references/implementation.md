# 实现路线与历史核对

## 当时实际采用的路线

基于 2026-10-30 对本地原始脚本、自动化配置和 GitHub Pages 设置的只读核对：

1. `study_calendar.py` 从 Markdown 学习计划解析每天的日期、时间段和任务；还可合并结构化作业、刷题计划以及昨日完成清单中的欠账。
2. 生成 `.ics`，同时写一份固定别名 `study-plan.ics`。固定文件名使手机不必每次换订阅地址。
3. PowerShell 更新脚本重新生成文件，复制到专用发布仓库 `calendar_publish`，执行 Git 提交和推送；以互斥锁防止多次更新同时运行，并保存日志。
4. [公开仓库 study-calendar](https://github.com/wudi-tech/study-calendar) 的 Pages 从 `main` 分支根目录发布。本次读取 Pages API 的状态是 `built`，HTTPS 已启用。
5. 手机通过固定的 `https://wudi-tech.github.io/study-calendar/study-plan.ics` 订阅。仓库原 README 明确说明用途为 Apple Calendar subscription。
6. 曾配置每天 08:00 运行本地发布脚本的 Codex 自动化。本次核对时状态是 **PAUSED**；不能因为配置文件存在就称其仍在自动更新。

原始本地脚本不是公开仓库中的完整内容。此包保留通用技术路线，示例生成器是为复用重新编写的精简实现，没有复制个人备考规则或作业数据。

## 三种接入方式如何选

| 方式 | 适合 | 需要理解的行为 |
|---|---|---|
| 一次性导入 ICS | 一次性活动，不要求以后跟随变化 | 重新发布网址中的文件，不等于修改已导入的副本 |
| 固定 URL 订阅 ICS（本 skill） | 已在使用的学习计划、课程和公开安排 | 首次订阅后客户端自行拉取；刷新并非实时推送 |
| 已授权的日历连接器/API | 私密日程、直接编辑账户、双向或更及时的写入 | 需要相应服务与权限，不能声称此技能已接通 |

用户明确指定服务时，按该服务执行；不能把所有日历请求都引导为公开 Pages。

## 抽取时保留和改进了什么

| 原始实现中的做法 | 可复用版本 |
|---|---|
| 固定订阅文件名，GitHub Pages 托管 | 保留，不随每次日程更新更换 URL |
| 事件 UID 取决于日期、时间、标题、描述的哈希 | 新 feed 从永久 `feed_id + id` 派生 UID；改时间时身份不变 |
| 原始文件没有 VALARM | 示例可按要求写入提前 N 分钟的 DISPLAY 提醒；仍需设备端测试 |
| 原始生成逻辑包含固定考试日期和本机路径 | 通用 JSON 输入，不依赖个人文件夹、考试或课程 |
| 原脚本更新后检查仓库状态并提交 | 新发布脚本先拒绝已有变更和无关的未推送提交，只暂存目标 ICS |
| 原脚本无变化时不推送 | 新脚本允许重试上次已提交但推送失败的 feed 更新 |
| 计划任务负责触发 | 保留为独立层；不把“技能存在”当作“任务已运行” |

**这些是技能包的能力，不代表原订阅已被迁移。** 新增的 [多来源选项](multi-source.md) 可以直接把原 ICS 作为来源，保留旧 UID 后添加新事件，无需先重建旧事件。若要把旧事件全部改写为 JSON，仍需建立 UID 映射或扩展原生成器；本包没有旧事件自动转 JSON 的迁移器。不要把仅含新事件的输出直接覆盖旧订阅。

原 Windows 写文件方式可能产生重复回车（CRCRLF）。合并器读取时会规范化这种换行，不改原来源文件，再由解析库输出规范 ICS。该兼容行为已有回归测试。

## 成功标准分层

生成成功 → 文件内容有效；推送成功 → 源码仓库已更新；远程 ICS 比对成功 → Pages 已提供目标版本；设备显示正确 → 客户端已获取；实测通知 → 当前设备提醒有效。每一层需要自己的证据。

规范参考：[RFC 5545](https://www.rfc-editor.org/rfc/rfc5545) 定义事件、UID、版本、时间和提醒的基础格式；[GitHub Pages 发布来源](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site) 说明分支与目录配置。
